# Integration contract

React / Vite / TypeScript SPA and FastAPI sync SQLAlchemy 2 backend. API prefix `/api`. Production PostgreSQL + Redis. UUID strings, SQL timestamps naive UTC internally (serialize UTC); monetary values decimal strings. Lists `{items: [], total: n}`. Error FastAPI `{detail: message}`. No public signup. Never use real remote credentials or modify real sites during tests.

**Current scope (2026-09-11):** [CORE_FUNCTIONS.md](CORE_FUNCTIONS.md) defines the retained business and nine retired empty tables. [SETTLEMENT_ORDERS.md](SETTLEMENT_ORDERS.md) defines the only current settlement workflow: immutable order headers and detail snapshots using current rates and observed consumption, with incremental baselines preventing repeat settlement. `/settlements/groups` returns the current state directly as `settlement`, without legacy `financials` or a nested `order`. The `/bills` UI and old bill/payment APIs are removed. Channel management remains free of settlement UI.

## Frontend HTTP interface

Use credentials=include. Session cookie HttpOnly; login returns `{user,csrf_token}`, keep CSRF in memory, pass `X-CSRF-Token` on writes; GET `/auth/me` returns same wrapper. CSRF check for authenticated unsafe methods. Write endpoints generally return created/updated object. GET lists wrapper.

### Request lifecycle and loading

- `api(path, method, data, signal?)` accepts an optional `AbortSignal`. `useData(path)` owns one request resource per path and authenticated session; a null path disables the request. A refresh cancels an earlier read of that resource, and cleanup cancels reads on path/session changes or unmount. Late results cannot overwrite the current resource; confirmed `setData` updates cancel older reads. There is no shared cross-page or cross-session response cache.
- The API client checks the session revision before applying a returned CSRF token or dispatching session-expired events. Responses from an earlier login are discarded, including late 401 responses. Aborted reads do not replace the current data/error state with cancellation errors.
- Route page modules are imported lazily behind loading/error boundaries. Shared modules can serve multiple routes. The production Nginx configuration compresses eligible static HTML, CSS, JavaScript, and SVG responses with gzip and retains immutable caching for hashed assets; the HTML entry remains uncached.
- User management, both channel views, and settlement history use the shared server-pagination control. User management requests 50 rows per page rather than implicitly fetching all authorized pages. Search/filter changes return to the first page; successful refreshes that shrink the result set repair an out-of-range page.
- The first performance pass required no schema change. The subsequent scope reduction introduces migration `4f8b27c93a10`, removes the unused bill/payment APIs and their aggregates from both user views, and preserves current order history and authorization rules. See [the scope and migration contract](CORE_FUNCTIONS.md).

### Hover details

- Use the shared `components/Tooltip` and root `TooltipProvider` for hover/focus descriptions. Native HTML `title` hints are removed; page/dialog `title` props remain headings. `Select` and `DateTimePicker` route their optional `title` prop through this component.
- Hints share a white rounded surface, blue-gray border and shadow, with portal placement above dialogs and automatic viewport avoidance. Full IDs, model names and upload labels use monospace text; long descriptions wrap and scroll. Static focused detail labels support arrow/PageUp/PageDown scrolling; Escape dismisses the hint before its containing dialog.
- Disabled controls retain native `disabled` and original action checks. A focusable wrapper exposes their explanation without enabling the action. Existing `aria-describedby`, field validation, dropdown keyboard behavior and modal focus trapping are retained. Keep interactive actions such as editing and confirming in the existing dialogs/popovers rather than tooltip content.

### Rates and account group selection

- GET `/discounts?payee_id=` returns version history and the 11 service projections. POST `/discounts` accepts `{payee_id,category_id,service_variant?,percent?,inherits_category?,effective_at?}`. Percent is 0–100 with at most 6 decimal places. A category default applies unless the service has an independent effective version; inheritance creates a new version instead of deleting history. Past effective times are rejected; explicit future versions are supported. There is no payment-conversion rule API.
- User management provides **Settle**, **Set rates** and **Settlement history** actions. Settle opens the account selector at `/users?account_id=...`; history opens that account's modal without navigation. Only the actual payer may edit the chosen payee's rates. Set rates displays service cards with save-on-blur inputs and version history. Unchanged/invalid values do not submit; failed saves preserve the draft. The UI omits `effective_at`, so saves become effective at server time. Missing or failed reads do not become a default zero.
- Account creation persists category defaults of 0%, effective from creation time; startup idempotently fills missing defaults without replacing existing versions. A valid 0% is permitted for current orders and produces a zero payment. New confirmations use current effective service rates; completed orders retain their original rate snapshots.
- GET `/settlements/groups?account_id=&search=&offset=0&limit=50` returns `{account:{id,username,nickname,role},items:[{id,display_id,owner_id,owner_name,owner_username,group_id,group_tag,category_id,category_name,variant,service_name,service_name_en,created_at,archived,remote_usage_total,settlement}],total}`. Admins may select only direct members; superadmins may select admin/member accounts. An admin account includes self plus direct members; a member includes self only. Archived channels remain included. Search matches group metadata, uploader or numeric ID, using literal LIKE escaping. Stable pagination uses `created_at DESC, id DESC`, offset >= 0, and limit 1–100. This read creates no orders and returns no credential/proxy fields.
- `settlement` is directly the current order projection, including `can_manage`, `can_settle`, `status`, `reason`, `payee_id`, `payee_name`, `group_state`, current rate and incremental amounts. There is no nested `settlement.order`, legacy `financials`, or separate `/settlements/group-status` endpoint. Frontend selection and amounts consume the same projection.
- Group readiness requires any current identity-matched remote target to be automatically disabled, or every target in a nonempty group to be confirmed disabled. Pending creates and unknown targets prevent the all-disabled condition. Complete known USD consumption from the latest saved successful observation is also required. Account loading, preview and confirmation do not synchronize remote sites; missing observations must wait for a successful background cycle. Current and previous per-target counters determine new usage; unchanged counters cannot create another order.
- Group tables keep cumulative remote consumption distinct from the increment to settle. Monetary calculations use decimal arithmetic: incremental consumption times the current percentage / 100, rounded half-up to eight decimal places per line. Selection totals sum those rounded values, deduplicating group IDs. Loading, failed, partial or invalid observations cannot be treated as known zero. Selection is reset when its account, search, page or refreshed data changes.

### Settlement orders and retired schema

- POST `/settlement-orders/preview` accepts `{channel_ids:[...]}` (1–100 entries) and returns a read-only quote with a `snapshot_hash`. POST `/settlement-orders` accepts the IDs, hash and `idempotency_key`; it rechecks permissions, parties, remote state, consumption, effective rates and previous orders, then commits the whole selection atomically. Different payees/layers, duplicate selected remote targets, invalid conversions or counter decreases reject confirmation.
- Orders record a completed settlement, not a transfer or an independently payable bill. GET `/settlement-orders` supports `account_id`, frozen recipient `payee_id`, search and offset/limit pagination; GET `/settlement-orders/{id}` returns frozen header/details to authorized parties or superadmins. There are no update/delete endpoints. Repeated requests with the same actor/key and payload return the original order; a changed payload cannot reuse a key. Upper and lower payer/payee relationships remain independent.
- `SettlementOrderLine` amount columns are only `usage_amount` and `payment_amount`, plus its recorded percentage. The internal `site_amounts` JSON retains per-target cumulative counters, prior baselines, incremental consumption, raw quota/conversion evidence and timestamps. Those fields are needed for repeat-settlement protection and are not exposed as extra cumulative amount columns. New orders use `SOYYYYMMDD...` without hyphens; display and search normalize older number spelling without rewriting stored IDs.
