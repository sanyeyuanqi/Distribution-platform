# Settlement orders

User management handles settlement through an order and one immutable detail row per selected channel group. Settlement history lists those orders. This is the current settlement workflow; the former fact-based bill preview, `/bills` page and independent payment APIs are removed. Migration `4f8b27c93a10` retires their empty tables and rejects any nonempty legacy table before removal. See [current scope and migration protection](CORE_FUNCTIONS.md).

## Recorded values

`SettlementOrder` stores the order number, settlement time, acting account, payer, payee, settlement layer, line count, total usage and total USDT amount. Each `SettlementOrderLine` stores the original group and category labels, uploader identity, rate version and percentage, consumption settled this time and the resulting USDT amount. Its amount columns are `usage_amount` and `payment_amount`; migration `7a3d91f0c6b2` removes the redundant `cumulative_total` and `previous_total` columns. Names and rates are snapshots, not live joins for historical display.

New order numbers use `SOYYYYMMDD` followed by the uppercase identifier suffix, without hyphens. History and detail responses also display older numbers without hyphens, while preserving their stored identifiers. Order-number searches accept either spelling.

The current category/service discount is the settlement rate. The initial rate is 0% from account creation. Amount = consumption being settled × percentage / 100, rounded half-up to eight decimal places per line. Order totals sum those rounded line amounts. The first order uses the observed total; subsequent orders use only new consumption from the same remote target in the same payer/payee/layer relationship.

Source consumption retains its decimal precision. Internal `site_amounts` target snapshots preserve site ID, remote ID, baseline and current amount for incremental calculation; raw remote responses, credentials and keys are never copied into orders. These target counters are not displayed as order-detail amount columns. Inactive target baselines remain available to prevent repeat settlement after a target reappears or moves to another local group. Removing the redundant aggregate columns preserves these snapshots, historical settlement amounts and recorded rates. Live group projections can still calculate current and previously settled totals from the target evidence.

## Confirmation and history

- `POST /settlement-orders/preview` accepts `channel_ids` and returns a read-only quote with `snapshot_hash` and frozen-value candidates.
- `POST /settlement-orders` accepts those IDs, the quote hash and an `idempotency_key`. It rechecks authorization, ownership, consumption, rate and previous orders before recording the whole selection atomically. Channels do not need to be disabled first.
- `GET /settlement-orders` supports account/payee/search filters and pagination. The `payee_id` filter matches the frozen order recipient, consistent with the account table's settlement count and amount; the existing `account_id` filter continues to select orders associated with that account's uploaded groups. `GET /settlement-orders/{id}` returns the immutable header and lines. Only authorized settlement parties and superadmins can read them.
- There are no update or delete endpoints. This workflow records a completed settlement; it does not initiate a transfer or create a legacy payment.

`GET /users` adds `settlement_order_count`, `settlement_order_amount` and `settlement_order_unit` to each visible account. These read-only statistics count settled order headers whose frozen `payee_id` is that account and sum their USDT payment amounts. An order with several lines counts once; a zero-amount order still counts. Superadmins see all such orders, while administrators see only orders they paid. Child-account receipts and the account's outgoing settlement amounts are not added to its receipts. Accounts without matching orders return `0`, `"0"` and `"USDT"`; amounts remain exact decimal strings.

The account table's cumulative consumption uses `GET /users` → `remote_usage_total`, with exact decimal `amount`, `unit: "USD"`, and `covered` / `total` target counts. It sums the latest locally synchronized NewAPI channel observations across all sites for the account and its existing direct-child team scope, including archived local groups. Each `(site_id, remote_id)` counts once; deleted targets are excluded, and conflicting or missing observations remain unknown or partial instead of being treated as zero. An account with no current remote targets returns `{"amount":"0","unit":"USD","covered":0,"total":0}`. Historical `usage_by_unit` facts remain separate and are never added to current remote counters. New counter snapshots come only from background scheduled synchronization. Account reads and Refresh fetch local data; preview and confirmation do not trigger a preceding remote sync. With no successful valid observation, consumption remains unknown instead of zero. The default cycle is about five minutes, subject to active batches and queue delay; see [automatic synchronization](AUTOMATIC_SYNC.md).

Enabled, disabled and mixed-state groups can be settled at any time from their saved observations; remote enable/disable state is informational and is not a settlement prerequisite. Complete, known USD observations are still required. A first known zero total or zero rate may be recorded. Unchanged counters cannot create another order; a counter decrease, duplicate target in one selection or partial/unknown consumption must be resolved before confirmation. Selections spanning different payees or layers are rejected.

Upper and lower settlement layers remain independent. Concurrent confirmations are serialized on the payee and lock the selected channel/distribution records; repeated requests with the same key and payload return the original order. The old claim-table guard is removed together with that subsystem; the retirement migration's nonempty check prevents silently discarding old claims or bills. Deployments containing such history must resolve that data separately before upgrading.

## UI

The user management table combines lifetime usage, settlement order count and total settled amount with **Set rates**, **Settle**, and **Settlement history** actions. Settle opens the account's group selector directly at `/users?account_id=<account ID>`. Settlement history opens a modal on the user management page for that account's receipts, matching its order statistics. Its payee filter stays fixed while search, refresh and pagination use local state without changing the page URL. Viewing an order opens its details above the history modal; closing details restores the history list, and closing history preserves the user list's current position and search. Set rates uses the channel-category discount cards with existing payer permissions. Saving a rate or completing a settlement refreshes the user list. Completed orders retain their recorded rates and amounts; a 0% rate produces a zero payment for new orders.

The sidebar's **Settlement history** entry opens the order list at `/settlements`; its header only shows Refresh. The former `/settlement-orders` address redirects there while preserving its filters. Eligible group selections in user management open a single confirmation dialog showing the rate, settlement consumption and payment amount. Confirming opens the newly created order with the same detail columns. Channel management continues to contain no settlement actions or records.
